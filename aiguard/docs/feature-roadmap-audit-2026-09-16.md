# AiGuard 能力盘点与功能提升建议（2026-09-16，基于 v0.1.1）

> 依据：对仓库全量源码的通读与逐点核实（HEAD = `9b8a56d`，v0.1.1，2026-09-15 发布，工作区无源码改动）。口径：每条能力标注 文件:行 实证；建议服从三条硬约束——内网明文上游可接管、三平台同等投入、单人维护且生产依赖零新增（仅预批 argon2 / git CLI）；请求侧性能预算 p99 < 2ms；第一痛点是误报。与《误报率与误拦截率诊断及优化方案》（docs/false-positive-audit-2026-09-16.md，下称「误报报告」）重叠的项不再展开，只引用归并。

## 二、功能提升建议（按 业务价值 × 实现成本 综合排序）

> 量级口径（单人全职）：S=1 天内、M=1–3 天、L=3–10 天、XL>10 天。降误报主线（命中反馈闭环、拦截可信度分级、三层豁免、灰度、规则版本化、样本回流、评估集、语义外置、指标面板、SSE/危险指令降噪）整体归近期，见误报报告方案 1–10，本清单不重复。

### 近期

**1. 内网明文上游接管闭环（CustomHostRule）**
- 解决的问题：私有化部署用 vLLM/Ollama 走 HTTP 明文 + 内网 IP 直连，当前无法完整接管：自定义域名仅精确主机名匹配（state.rs:1242-1245，normalize 剥端口后比对），不支持网段/端口/后缀；透明层靠 SNI 识别（transparent.rs:1），内网 IP 直连无 SNI；核查执行器对明文上游发不出请求（link_check.rs:218 硬编码 `https://`）。
- 大致实现思路：把 `custom_hosts: Vec<String>` 升级为结构化 CustomHostRule（exact/suffix/cidr/hostport 四种匹配），状态层与代理判定（proxy.rs:131-143）改走统一匹配函数；link_check 的 URL 构造按规则 scheme 明文直发；对内网 IP 直连场景明确走「显式 http_proxy 指向本地代理」引导，不做透明拦截（诚实边界，见第五章）。
- 影响范围与触及模块或文件：src-tauri/src/state.rs（规则结构+匹配）、proxy.rs（判定与明文转发分支）、link_check.rs:218（scheme 感知）、proxy_config.rs（PAC 对 IP 字面量的限制说明）、src/App.tsx（规则编辑 UI）。
- 改动量级：L。
- 验证方式：本机起 vLLM/Ollama 明文端点 → 配 hostport 规则 → 断言请求被脱敏、响应还原、核查报告可出；配 CIDR 后断言网段内主机命中、网段外不命中；既有 25+17 内置域名行为不变（回归 proxy.rs 测试）。
- 近期或长期：近期。

**2. 环境变量凭据键名锚定接入请求侧主路径**
- 解决的问题：「密码/私有令牌没有固定格式」是请求侧最大漏报面——6 条内置规则全靠值形态，无键名语义。现成武器 ENV_CRED_RE（`<大写>_(KEY|TOKEN|SECRET|PASSWORD|…) =` 形状 + 长度 20 + 熵 3.0 + 有序序列排除，audit.rs:334-343）已实现但只用于响应侧报错扫描（audit.rs:400），请求侧主路径未接。
- 大致实现思路：把该模式连同熵校验移植为请求侧的键名锚定扫描（对 JSON 请求体按「键名匹配 + 值熵达标」出 Mask 命中，独立开关默认开）；键名锚定天然低误报，正对第一痛点。
- 影响范围与触及模块或文件：core/src/audit.rs（模式与熵函数已是 pub 内部件，复用）、core/src/detector.rs（新增锚定扫描段，类似 locker 追加段 detector.rs:482-491）、src-tauri/src/commands.rs（配置开关）、src/i18n-dict-ui.ts（新文案键，过 `npm run i18n:check`）。
- 改动量级：S（M 含 UI 开关与测试）。
- 验证方式：构造 `{"config":{"db_password":"<高熵20+>"}}` 断言命中并替换；`db_password="123456"` 低熵不命中；`FOO_TOKEN=abcdefg...` 有序序列不命中；既有单测（audit.rs:1480-1490）迁移为请求侧断言。
- 近期或长期：近期。

**3. 请求侧规则覆盖缺口补齐（第一批移植 + 第二批按需）**
- 解决的问题：审计响应侧已有成熟凭据形态库（JWT/PEM 私钥/Bearer/连接串密码/AWS Key 等，audit.rs:309-331、293-299），但请求侧脱敏只有 6 条内置正则——用户把含 JWT/PEM 的文本发给 AI 时不脱敏。缺口清单（语义名→展示名）：连接串密码/PEM/JWT/Bearer/AWS Key/座机/车牌/MAC/IBAN/统一社会信用代码。
- 大致实现思路：第一批直接移植审计侧已验证正则为内置脱敏规则（连接串密码/PEM/JWT/Bearer/AWS Key 五类，形态成熟、误报面已知）；座机/车牌/MAC/IBAN/统一社会信用代码为第二批，需新写结构正则与校验器，按用户实际频率决定。**陷阱**：新增内置规则必须同步 `default_rule_specs()` 与 `preset_table` 三档条目（条目数精确一致），否则存量用户的档位被 `preset_of_specs` 误判为 custom（detector.rs:289-304 的全一致反推逻辑，缺 id 即 `unwrap_or(false)`）。
- 影响范围与触及模块或文件：core/src/detector.rs（default_rule_specs:176、preset_table:246、PiiKind 枚举）、commands.rs（恢复默认逻辑）、src/App.tsx（规则卡片）、src/i18n-dict-ui.ts。
- 改动量级：M（第一批）/ L（含第二批）。
- 验证方式：每条新规则配正/负样本单测（沿用 detector.rs 测试风格）；升版本后断言老用户档位判定不漂移（构造存量 specs + 新 default 跑 preset_of_specs）。
- 近期或长期：近期。

**4. 主动核查跨平台修复（curl 命令名平台感知）**
- 解决的问题：核查执行器硬编码 `Command::new("curl.exe")`（link_check.rs:284），`#[cfg(target_os="windows")]` 只用于隐藏黑窗（link_check.rs:302-306）——macOS/Linux 上没有 `curl.exe`，主动核查在三平台策略下于非 Windows 平台必然失败。三平台同等投入约束下的存量缺陷。
- 大致实现思路：命令名按平台取 `curl` / `curl.exe`（或先探测 PATH）；补一条非 Windows 的集成冒烟测试说明；顺带把「核查依赖系统 curl」写进设置页自检（curl 缺失时给出可读提示而非静默 status=0）。
- 影响范围与触及模块或文件：src-tauri/src/link_check.rs:271-338、commands.rs:1135（错误提示）、src/i18n-dict-ui.ts。
- 改动量级：S。
- 验证方式：Windows 与 macOS/Linux 各跑一轮 full profile 核查，断言 step 状态非 0 且有效回执数一致。
- 近期或长期：近期。

**5. 请求侧性能基准护栏（p99 < 2ms 预算）**
- 解决的问题：「无感还原」是产品承诺，但仓库无任何 bench（无 benches 目录），正则集扩大（建议 3）、键名锚定（建议 2）落地后性能回归只能靠手感。
- 大致实现思路：core 加 benches（criterion 仅 dev-dependency，不进生产依赖，符合零新增策略）或零依赖手写计时基准：固定语料（含中文长文本 + 大 JSON + 多命中）跑 `Detector::scan/scrub`，输出 p50/p99；CI 设阈值告警（超 2ms 失败）。同时记录 `scrub_json_value` 端到端路径的基准。
- 影响范围与触及模块或文件：core/Cargo.toml（dev-dependencies）、core/benches/（新）、scripts/（CI 门禁脚本）。
- 改动量级：S。
- 验证方式：基准在当前规则集下产出基线数字；人为塞入病态正则断言 CI 失败。
- 近期或长期：近期。

**6. 覆盖边界诚实披露页（防不了什么，写进界面）**
- 解决的问题：产品存在原理性盲区，用户不知情时会把「没报」当「安全」：本地 CLI 直连 MCP 的流量不经代理（防不了）；内网 IP 直连不经透明层（无 SNI，需显式配 http_proxy）；Windows CA 私钥无法导入系统证书存储（CNG 不可导出）；记忆残留只能靠主动核查（被动流量看不到）；语义层判不准的宁可漏报。
- 大致实现思路：设置页新增「防护边界」说明卡（静态内容 + 每条附当前状态自检，如「检测到 curl 经代理：已覆盖」复用进程审计 state.rs:764-771 的能力）；不做任何伪自动化。
- 影响范围与触及模块或文件：src/App.tsx、src/api.ts（MOCK 对齐）、src/i18n-dict-ui.ts（新增文案键必须进词典，`npm run i18n:check` 校验）。
- 改动量级：S。
- 验证方式：中英双语切换后无漏译（i18n 自检全绿）；自检状态与实际进程列表一致。
- 近期或长期：近期。

**7. 审计事件与请求日志导出（CSV/JSONL）**
- 解决的问题：私有化场景的合规取证与留存审计目前只能截屏；同时它是误报报告方案 6（隐私内样本回流）的载体前置——导出物天然全脱敏（evidence 只含类型/长度/哈希，audit.rs:200-207），可直接作为离线样本。
- 大致实现思路：新增命令 `export_audit(from_ts, to_ts, format)`，按既有分页查询（commands.rs:925）流式写 CSV/JSONL；列 = AuditEventRow 全字段（store.rs:40-65），不含原文；前端在审计页加导出按钮 + 系统文件对话框（复用 tauri-plugin-dialog）。
- 影响范围与触及模块或文件：src-tauri/src/store.rs（查询复用）、commands.rs、src/App.tsx、src/api.ts、src/i18n-dict-ui.ts。
- 改动量级：S。
- 验证方式：导出 1000 条事件 → 文件行数与 SQL count 一致；抽查任意行不含请求原文子串（可断言 evidence 不含 `[[PII:` 之外的原文片段形态）。
- 近期或长期：近期。

**8. i18n 自检递归化 + App.tsx 拆分（工程前置）**
- 解决的问题：App.tsx 已 5375 行（App.tsx:5097-5107），任何新 UI 都在继续增重；而自检脚本 `FRONTEND_FILES` 硬编码三文件（i18n_check.mjs:60），一旦拆出新文件，新 t() 调用逃过检查且 check 全绿——拆分前必须先修脚本，否则词典义务失效。
- 大致实现思路：第一步 S：i18n_check.mjs 改为递归扫描 src/ 下 .ts/.tsx（沿用现有 TS AST 遍历，排除 dict 文件本身）；第二步 M：按页面域拆组件（home/requests/rules/security/audit/settings 六块，App.tsx:5099-5104），行为零变更纯搬家，拆完 `npm run i18n:check` 与构建全绿。
- 影响范围与触及模块或文件：scripts/i18n_check.mjs:60、src/App.tsx（拆出 src/components/ 等）、src/i18n.ts（t 定义不动）。
- 改动量级：S（脚本）+ M（拆分）。
- 验证方式：脚本改动后构造一个含未入词典 t() 的新文件断言 check 报错；拆分前后快照对比 UI 文案与行为零 diff。
- 近期或长期：近期（脚本先行，拆分随后）。

**9. 便携版支持（免安装目录 + argon2 加密）**
- 解决的问题：三平台同等投入约束下的分发形态：U 盘/受控环境需要免安装运行，数据目录不能写进系统用户目录。
- 大致实现思路：数据目录解析加「便携标记文件」分支（exe 同级 portable.marker → 数据落 exe 同级 data/）；存量 kv（令牌/CA 私钥等 DPAPI 密文）在便携模式下用 argon2 派生密钥加密（唯一预批的可选依赖；未设置口令时沿用现 DPAPI/明文降级路径并告警，沿用 security.rs:483-494 的 `enc:` 前缀扩展）。
- 影响范围与触及模块或文件：src-tauri/src/main.rs（目录解析）、state.rs:1067-1100（令牌落盘路径）、security.rs（argon2 分支）、打包脚本。
- 改动量级：M。
- 验证方式：同一份便携目录在两台机器可用（有口令时）；普通安装版升级不受影响（回归 state.rs 令牌测试 state.rs:2092-2128）。
- 近期或长期：近期。

**13. 凭据使用检测与轮换提醒（新增于开发方案讨论轮）**
- 解决的问题：模型需要真实密钥访问外部服务时，默认脱敏会让调用失败（用户困惑「为什么没成功」），豁免放行则真实密钥明文出站给 AI 服务商（需要轮换）——两条路都需要在响应完成后给出对应提醒，形成「用完即改」闭环。
- 大致实现思路：以**保险柜凭据值实际命中**为触发器（不用 locker_access 键名提及，防噪音，见误报报告 2.2.10）；命中时按「脱敏放行 / 豁免放行」分两路写入内存聚合器（按条目去重 + 冷却窗口合并计数）；响应完成（SSE 结束 / 非流式响应完成）时触发——A 路（已脱敏）UI 横幅「该条目已脱敏，模型若需真实密钥无法工作」；B 路（明文外发）高优先提醒「真实密钥已外发，建议立即轮换」，未聚焦走系统通知、已聚焦走 UI 横幅（对通知克制规则的有意例外，仅 B 路）。提醒内容只含条目名/时间/次数，绝无密钥值。
- 影响范围与触及模块或文件：src-tauri/src/proxy.rs（命中/放行打点）、src-tauri/src/state.rs（聚合器 + 通知变体，复用 dispatch_notification 三条克制规则）、src-tauri/src/commands.rs（开关）、src/App.tsx、src/i18n-dict-ui.ts。
- 改动量级：S–M（MVP 无新表）。
- 验证方式：含保险柜条目值的请求 → 断言 A 路横幅出现且计数正确；豁免放行 → 断言 B 路轮换提醒；同条目冷却窗口内多次命中 → 断言合并为一条。
- 近期或长期：近期。

### 长期

**10. 场景模式（会话级检测强度手动切换）**
- 解决的问题：三档预设是全局粒度，「写代码场景」与「贴合同场景」的最优检测强度不同；全自动场景识别不可行（见第五章），可行解是手动会话级档位。
- 大致实现思路：在活跃会话列表（state.rs:1348-1401）上做会话级预设覆盖（复用 apply_preset_to_builtin 的产物做会话维度快照，响应侧审计门槛也可随会话降/升）；显式手动，不做自动分类。
- 影响范围与触及模块或文件：state.rs（会话元信息扩展）、proxy.rs:297-310（取会话级快照）、src/App.tsx、src/i18n-dict-ui.ts。
- 改动量级：M。建议在误报报告方案 1（命中反馈闭环）产出数据后再动手，避免无数据瞎分档。
- 验证方式：同一会话切「写作档」后手机号仍脱敏、IP 不再报；跨会话互不影响。
- 近期或长期：长期。

**11. 策略同步与企业策略下发（git CLI + argon2）**
- 解决的问题：多设备/小团队的一致策略需求：规则、名单、保险柜条目手工逐台维护。当前已有规则包 aiguard.rules v1 导入导出（commands.rs:429-546）可作为传输格式。
- 大致实现思路：规则包格式扩展为「策略包」（规则+名单+语义配置+保险柜条目），同步走外部 git CLI（克隆/拉取用户指定私有仓库，允许的依赖）+ argon2 加密静态段；冲突策略取「远端为准 + 本地变更提示」，不做实时服务端（零服务、零新增生产依赖）。
- 影响范围与触及模块或文件：commands.rs（导入导出扩展）、state.rs（配置装载序）、core/detector.rs（规格版本字段，配合误报报告方案 5 规则版本化）、src/App.tsx、src/i18n-dict-ui.ts。
- 改动量级：XL。
- 验证方式：两台设备指向同一仓库，A 改规则 B 拉取生效；含 argon2 段的包在无口令设备上拒载并提示。
- 近期或长期：长期（前置：确认真实多机需求与合规边界，见第四章）。

**12. ONNX NER 可选语义层（默认关，独立模型分发）**
- 解决的问题：中文姓名/机构启发式（semantic.rs:16-21）召回有限；真 NER 能补，但推理 10–50ms 与请求侧 p99 < 2ms 冲突，绝不能默认启用。
- 大致实现思路：语义引擎加可选 ONNX 后端：模型文件独立下载不进安装包；仅在用户显式开启 + 会话级开关下加载；默认全关时零开销（保持 semantic.rs 现有纯启发式路径为默认）；与建议 5 的基准联动，开启态单独记录性能档位。
- 影响范围与触及模块或文件：core/src/semantic.rs（引擎 trait 化）、core/Cargo.toml（可选 feature）、打包脚本（模型下载器）、src/App.tsx、src/i18n-dict-ui.ts。
- 改动量级：XL。
- 验证方式：关闭态基准与基线一致（零回归）；开启态单独输出 p99 并在 UI 明示「已启用重模式」。
- 近期或长期：长期。

## 四、需要用户补充的关键信息

1. **内网明文上游的真实形态**：vLLM/Ollama 的 host:port 清单、是否统一网段、是否偶有自签 TLS——决定 CustomHostRule 四种匹配（exact/suffix/cidr/hostport）的优先级与明文直通分支的默认面。
2. **主力客户端形态**：网页版 / CLI / SDK / IDE 插件的比例，尤其是否存在本地 CLI 直连 MCP 的日常用法——决定「覆盖边界披露页」的措辞强度，以及明文直通分支走系统代理还是显式 http_proxy 引导。
3. **多设备/团队下发是否已有真实场景**：仅个人多机（便携版 + 手动导包可能已够）还是确有多人一致策略（才值得做建议 11 的 XL 投入）。
4. **第二批规则（座机/车牌/MAC/IBAN/统一社会信用代码）的实际出现频率**：这些形态无现成正则可移植，需要新写并各自配校验器，按真实频率决定是否投入。
5. **审计保留期期望**：当前默认 7 天（state.rs:343），私有化合规若要求 30/90 天，与误报报告方案 9 的指标窗口一并定。
6. **便携版的口令策略**：是否接受「每次启动输入口令解锁数据目录」，还是仅加密敏感项（CA 私钥/令牌）——决定 argon2 的接入深度。
7. **请求侧键名锚定的默认档位**：默认全量开启，还是绑定三档预设（保守关/均衡开）——影响建议 2 的上线误报体感，建议默认开并纳入保守档例外。
8. **审计导出的格式偏好**：CSV（表格友好）还是 JSONL（机读友好，便于误报报告方案 6/7 直接消费），或两者都要——只影响建议 7 的一层序列化代码。

## 五、风险与依赖说明

**依赖零新增策略的落实**：上述 12 条建议中，生产依赖新增仅两处且均为预批项——建议 9（便携加密）与建议 11（策略包静态段加密）使用 argon2；建议 11 的同步通道走外部 git CLI（系统命令，非 crate）。建议 5 的 criterion 仅 dev-dependencies，不进生产构建；建议 4 反而消除一处平台假设。其余全部复用现有依赖（core 9 个 + src-tauri 现有栈，core/Cargo.toml:7-17）。

**实现陷阱（写代码前必读）**：
- 新增内置规则时 `default_rule_specs()` 与 `preset_table` 三档必须同步（条目数精确一致），否则存量用户档位被误判 custom（detector.rs:289-304）；有单测覆盖（detector.rs:583-625），改动后必须先跑它。
- 任何前端新 UI：新 t() 键必须进 src/i18n-dict-ui.ts，`npm run i18n:check` 校验；拆分 App.tsx 前必须先把 i18n_check.mjs:60 改为递归扫描，否则检查静默失效。
- 明文直通分支只对用户显式配置的内网 host 放行，不得扩大默认接管面；PAC 对 IP 字面量的覆盖限制需在 UI 如实说明。

**诚实不可行清单（严禁设计成可行，UI 只能标注或引导）**：
- Windows CA 私钥导入系统证书存储：CNG 不可导出，仅 DPAPI 降级（security.rs:147-234 现状已是最优解）。
- 记忆残留被动化：被动流量看不到跨请求行为，只能主动核查（link_check.rs）+ UI 标注。
- 内网 IP 直连透明拦截：无 SNI 即无法识别（transparent.rs:1-9），只能引导显式配 http_proxy。
- 全自动场景自适应：只能手动场景模式/会话级分类（建议 10）。
- ONNX NER 默认启用：推理 10–50ms 与 p99 < 2ms 冲突，只能可选不默认（建议 12）。
- 本地 CLI 直连 MCP 的流量不经代理，防不了（建议 6 披露）。

**其他风险**：
- proxy.rs 头注释写「hudsucker 0.20」，实际 Cargo.toml 已是 0.21（src-tauri/Cargo.toml:25）——文档漂移，升级 hyper/rustls 旧栈（hyper 0.14 系）时一并修正；该升级涉及 proxy.rs/transparent.rs 全量类型路径，单列任务，不与功能建议混做。
- 建议 1 的 CustomHostRule 与建议 3 的新增内置规则都触碰 detector/state 的配置装载序，建议先落建议 5 的性能基准再动检测路径，保证每次改动有基线可比。
- 误报报告与本文档的边界：本文档 13 条均不与其 10 条方案重复；若并行实施，其方案 1（命中反馈闭环）与方案 5（规则版本化）的落库字段变更应与本清单建议 7（导出）共享一次表结构变更，避免两次迁移。

*本文档所有 文件:行 均经源码逐点核实（含抽查 audit.rs:334、proxy.rs:948、link_check.rs:218、detector.rs:289、scripts/i18n_check.mjs:60）；未臆造任何不存在的模块或函数。*
